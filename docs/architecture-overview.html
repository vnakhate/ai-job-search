A job search that runs as prompts, not services.

This repo has no server, no database and no application code in the usual sense. It is a Claude Code workspace: twelve slash-command workflows and a nine-file methodology skill drive six small Bun CLIs that search job boards, a LaTeX toolchain that compiles tailored CVs and cover letters, and a handful of Python tools that verify what came out.

The candidate profile is the ground truth. Every workflow reads from it, and the drafting rules forbid any claim it cannot support. State lives in plain files next to the code, all of them git-ignored.

02 · The application loop

From profile to signed contract

Three commands form the core. The rest hang off specific stages. Each command is a markdown file with numbered steps the model follows in order.

STAGE 1 · ONBOARD
/setupBuild the profile
Reads documents/, a pasted CV, or interviews you. Writes CLAUDE.md and files 01, 02, 04, 05, 07.
/expand/reset/add-template/add-portal
STAGE 2 · DISCOVER
/scrapeSearch the boards
Runs every enabled portal CLI in parallel, dedups by company+title key, quick-scores fit, stores in seen_jobs.json.
WebSearch fallbackportal health check
STAGE 2b · TRIAGE
/rankBatch-score
Parallel agents fetch each posting and score five fit dimensions. Deal-breakers veto. Returns a ranked shortlist.
/upskill reads gaps
STAGE 3 · APPLY
/applyDraft, review, compile
Drafter-reviewer workflow with mandatory PDF compile and ATS text-layer check. Details in section 03.
salary_lookup.py08-application-forms
STAGE 4 · TRACK
/outcomeRecord what happened
Archives CV, letter and posting to documents/applications/. Follow-up drafts after 10 quiet days.
/gmail-sync/html-report/notion-sync
STAGE 5 · INTERVIEW
/interviewPrep pack
Stage-specific prep from the archived application, company research, STAR mapping, and an optional mock interview.
07-interview-prep
The loop closes. Once a few applications resolve, /outcome points back to /setup to recalibrate the fit framework from what actually got interviews. /setup --section search re-tunes the queries in search-queries.md without a full re-onboard.
03 · Inside /apply

Drafter, reviewer, compiler

The one command that produces documents. Two agents with separate contexts, one hard gate: the PDFs must compile, fit the page budget, and read cleanly to an ATS parser.

drafter (main agent)
reviewer (spawned agent)
toolchain gate
state write
STEP 0
Parse input
URL or pasted text. Posting is untrusted: no embedded instructions followed, no links fetched from its body.
STEP 1
Evaluate fit
Language Gate, then five dimensions from 04-job-evaluation.md. Presents verdict, asks to proceed.
STEP 2
Draft
cv/main_<co>_<role>.tex and the cover letter, from templates in 05 and 06, style rules in 03.
STEP 3
Review
Reviewer researches the company (verify-before-use), runs a Factual Grounding Audit against three sources, returns critique.
STEP 4
Revise
Drafter applies feedback. New facts the user confirms are written back to 01-candidate-profile.md in the same turn.
iterate
STEP 5
Compile & inspect
lualatex CV, xelatex letter. Read the PDF. CV exactly 2 pages, letter exactly 1, no orphaned titles. verify_layout.py measures it.
STEP 5d
ATS check
verify_pdf.py --dump-text: literal email and phone, no glyph garbage, sane reading order, keyword coverage without stuffing.
STEP 6
Present & record
Verification checklist, key tailoring decisions, tracker row, optional application-form field sheet.
Relevance-weighted cutting. When the CV overflows two pages, each line is scored on relevance to the posting, uniqueness, and whether the cover letter depends on it. The lowest total goes first, not the oldest.
Nothing invented. The grounding audit strips any claim absent from CLAUDE.md, the profile file and the master CV. That is why confirmed facts must reach the profile immediately or they vanish from every later draft.

Four kinds of artifact, four directories. Markdown carries behaviour; TypeScript and Python carry the few things that must be deterministic.

06 · Guardrails

What CI and the prompts refuse

Defences are instruction-level, not a sandbox. CI checks the framework; the prompts check the inputs; you check the code you copy in.

Trust boundaries in the prompts
  • Postings are untrusted input.No instruction embedded in a job ad is followed. No link found inside posting text is fetched. Company claims are verified only against independently located sources.
  • Reviewer research is not trusted either.The verification checklist re-verifies every company-specific claim via WebFetch or WebSearch before it reaches a document.
  • robots.txt gates retries.The browser-header curl retry in 09-web-research.md only runs when robots_check.py says the site permits it. Never to override a refusal.
  • Manual portal install, on purpose.Portal skills run pre-approved against your career data, so borrowing one from another fork is a copy-and-read-the-code step. There is deliberately no installer.
  • Reset needs a typed word./reset lists what it will delete and requires RESET before touching anything.
07 · Extension points

Three seams, no upstream changes

Market-specific things belong in forks. The framework exposes exactly three places to plug them in.

Portal skills

/add-portal investigates a job board (search URL pattern, result structure, access rules), scaffolds a CLI with the shared contract, test-runs a live query, and registers it. Auth-walled boards are declined. Community-built portals are catalogued in discussion #78.

Document templates

/add-template registers any toolchain that compiles to PDF from the command line: LaTeX, Typst, or other. It captures the compile command, fonts, style rules and page limit, runs a mandatory test compile, and writes an ACTIVE-TEMPLATE block that /apply honours.

Evaluation criteria

Deal-breakers and preferences are free-form lines in the profile. "No on-call" or "minimum salary X" carries real weight in /rank and /apply with no code. Language is the one structured gate: an undeclared required language hard-rejects, a lower declared level only flags.
